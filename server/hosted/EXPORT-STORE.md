# Private export object store

Project export archives are stored below one configured absolute root as:

```text
exports/<organization-id>/<project-id>/<export-id>/attempt-<attempt>-fence-<fence>.zip
```

The store accepts server-generated bytes only. Keys are derived from the
authenticated tenant and project; callers cannot supply a filesystem path.
Directories are mode `0700`, archive files are mode `0600`, symbolic links and
special files are rejected, and every read recomputes the stored SHA-256 and
byte count recorded in PostgreSQL.

Writes require a positive customer attempt and worker fence. They create and
`fsync` a private temporary file, then use an atomic no-overwrite hard link in
the same directory. Reusing an exact fenced key is idempotent only for
identical bytes. Different bytes fail with `OBJECT_KEY_CONFLICT`; stale workers
and manual retries therefore cannot overwrite one another.

Reads and cleanup retain support for the pre-v15 four-part legacy key so an
already-ready archive remains downloadable during migration. New writes can
only use the fenced five-part key.

PostgreSQL `ss.export_requests` remains lifecycle authority. Expiry workers must
first mark the request expired, then call the store with that exact recorded
object key. The store never performs a broad recursive deletion.

The hosted export worker is held by default. It starts only when
`SITESOURCERY_EXPORT_WORKER_MODE=enabled` is exact; any other nonempty value
fails startup. Batch, interval, and backoff settings are bounded by
`export-worker.mjs`. The hosted process passes its shutdown `AbortSignal` into
every batch, so a claim prepared before shutdown returns to `queued` before any
object write. Once an object write begins, the worker reconciles that exact
immutable key and either finalizes the matching fence or records bounded
manual-retry facts.

`backupManifest()` is the backup contract, not a backup. A production backup
job must copy every listed key and preserve its checksum on a separate,
encrypted failure domain. A restore is accepted only after every entry is back
under a `0700` root as `0600`, all checksums and byte counts pass, and a
PostgreSQL restore points to the same immutable keys. Restore drills must cover
both the database and object tree together.
